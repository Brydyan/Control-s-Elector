# Design — T-LEGAL-01: Privacy Policy + Terms of Use

**Date:** 2026-11-06  
**Status:** Design Phase  

---

## Decisiones Arquitectónicas

### D1: Política + Términos versionados (v1.0, v1.1, etc)

**Decision:** Cada actualización incrementa versión. Usuario debe aceptar nueva versión para continuar.

**Versioning Scheme:**
```
v1.0 = Initial release (2026-11-06)
v1.1 = Minor update (e.g., clarification on data retention)
v2.0 = Major update (e.g., new processing activity)
```

**Storage:** Versión en `usuario.accepted_terms_version` (String: "1.0", "1.1", etc)

**Why:**
- Legal documents change; need audit trail of what user accepted
- Incrementing version forces re-acceptance (compliance)
- Current version in `application.properties`: `legal.terms-version=1.0`

**Alternatives:**
- ❌ No versioning: lose audit trail, users accept once forever
- ❌ Dynamic admin panel: risky (legal changes need code review + signed-off)
- ✅ **Selected:** Static versionning, code-managed

---

### D2: Static HTML pages (git-managed, NOT database-driven)

**Decision:** `/privacy` y `/terms` servidos como archivos estáticos o embedded en JAR.

**Location:**
```
frontend/app/src/assets/legal/privacy.html (ES + EN)
frontend/app/src/assets/legal/terms.html (ES + EN)
```

Or backend:
```
backend/electoral-api-quarkus/src/main/resources/legal/privacy-v1.0.html
backend/electoral-api-quarkus/src/main/resources/legal/terms-v1.0.html
```

**Why:**
- Legal documents = security sensitive (no admin UI to edit)
- Version control ensures history (Git blame)
- Lawyer reviews + signs-off in PR before merging
- Static = faster serving, no DB query

**Alternatives:**
- ❌ Admin UI to edit Terms: too risky, compliance nightmare
- ❌ Database storage: adds query latency, harder to version
- ✅ **Selected:** Git + static files

---

### D3: Endpoints for policy/terms

**Decision:**
- `GET /privacy` → HTML estático (public, no auth)
- `GET /terms` → HTML estático (public, no auth)
- `GET /api/v1/legal/current-version` → Returns `{ "version": "1.0" }` (public)
- `POST /api/v1/user/accept-terms` → Accept + audit (auth required)
- `GET /api/v1/user/export-data` → GDPR export (auth required)
- `POST /api/v1/legal/contact-dpo` → DPO contact form (rate limited)

**Why:**
- `/privacy` y `/terms` are SEO endpoints (public, static)
- API endpoints for acceptance, export, contact are versioned (`/api/v1/`)
- Current version queryable (for modal to check if user needs re-acceptance)

**Alternatives:**
- ❌ Everything behind auth: SEO broken
- ❌ /api/privacy endpoint: less discoverable, static better for public pages
- ✅ **Selected:** Hybrid (public static + API versioned)

### D4: Terms Acceptance Audit Table

**Decision:** `terms_acceptance_audit` logs ALL acceptances (not just overwrite user.accepted_terms_version).

**Schema:**
```sql
CREATE TABLE terms_acceptance_audit (
  id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  usuario_id BIGINT NOT NULL REFERENCES usuario(id),
  terms_version VARCHAR(10) NOT NULL,  -- "1.0", "1.1"
  accepted_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  ip_address VARCHAR(45),  -- IPv4 or IPv6
  user_agent VARCHAR(500),
  locale VARCHAR(5),  -- "es_ES", "en_US"
  consent_type VARCHAR(50),  -- "initial", "update"
  FOREIGN KEY (usuario_id) REFERENCES usuario(id)
);

-- Also update usuario table:
ALTER TABLE usuario ADD COLUMN accepted_terms_version VARCHAR(10);
ALTER TABLE usuario ADD COLUMN accepted_terms_at TIMESTAMP;
ALTER TABLE usuario ADD COLUMN accepted_privacy_version VARCHAR(10);
ALTER TABLE usuario ADD COLUMN accepted_privacy_at TIMESTAMP;
```

**Why:**
- Audit trail: prove user accepted specific version at specific time
- GDPR compliance: legal proof if user disputes
- IP + User-Agent: detect suspicious acceptance patterns
- Separate audit table = efficient queries (usuario table not bloated)

**Alternatives:**
- ❌ No audit table, just update usuario: lose history
- ❌ Single "acceptance_at" without version: can't prove which version was accepted
- ✅ **Selected:** Detailed audit table

### D5: Modal in login flow (mandatory acceptance)

**Decision:** On login, before redirecting to dashboard:
1. Check if `usuario.accepted_terms_version < legal.terms-version`
2. If yes: show modal with Terms + Privacy links
3. User must click "Accept" to proceed (no "Decline" button)
4. If user closes modal: redirect to login page (logout)

**Frontend:**
```typescript
// authguard.ts
if (user.accepted_terms_version !== currentTermsVersion) {
  return this.router.navigate(['/terms-acceptance-modal']);
}
```

**Why:**
- GDPR: need explicit consent for Terms
- Election system: no opting-out (mandatory for access)
- Modal before dashboard: user must accept before seeing data

**Alternatives:**
- ❌ Checkbox on signup only: doesn't handle version updates
- ❌ Banner that can be dismissed: too passive
- ✅ **Selected:** Mandatory modal on login if version mismatch

### D6: Export Data endpoint (GDPR Art. 15)

**Decision:** `GET /api/v1/user/export-data` returns complete user record as JSON.

**Response Format:**
```json
{
  "exported_at": "2026-11-06T10:30:00Z",
  "user": {
    "id": 123,
    "email": "observer@example.com",
    "role": "OBSERVER",
    "created_at": "2026-11-01T00:00:00Z",
    "accepted_terms_at": "2026-11-05T14:00:00Z"
  },
  "actas_registradas": [
    { "id": 1, "jrv_id": 101, "estado": "ENVIADA", "created_at": "..." }
  ],
  "export_request_id": "uuid-123"
}
```

**Rate Limit:** 1 export per 24h (prevent abuse)

**Why:**
- GDPR Art. 15: user right to access personal data
- Format: machine-readable JSON (not PDF)
- Rate limiting: prevent denial-of-service

**Alternatives:**
- ❌ Paginated large exports: too complex
- ❌ No rate limit: 1000 exports/min DoS
- ✅ **Selected:** JSON, 1 export/24h limit

### D7: DPO Contact Form (not automated email)

**Decision:** Form POST to `/api/v1/legal/contact-dpo` stores message, manual DPO response.

**Schema:**
```sql
CREATE TABLE dpo_contact_requests (
  id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  name VARCHAR(255),
  email VARCHAR(255),
  subject VARCHAR(255),
  message TEXT,
  submitted_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  ip_address VARCHAR(45),
  status VARCHAR(50) DEFAULT 'NEW'  -- NEW, IN_PROGRESS, RESOLVED
);
```

**Why:**
- No automatic email: DPO might be offline, email gets lost
- Database log: audit trail (GDPR compliance)
- Manual response: DPO ensures quality

**Alternatives:**
- ❌ Direct email (no log): lose audit trail
- ❌ Auto-response: might promise what DPO can't deliver
- ✅ **Selected:** DB + manual DPO review

## Flujo de Aceptación

```
[Usuario loguea]
    ↓
[AuthGuard: check current_terms_version]
    ↓
[¿usuario.accepted_terms_version < current?]
    ├─ NO → redirect /dashboard (normal flow)
    └─ SÍ → show TermsAcceptanceModal
         ├─ Modal muestra Privacy link, Terms link
         ├─ User lee (puede hacer click)
         ├─ User hace click "Acepto"
         │    ↓
         │    [POST /api/v1/user/accept-terms]
         │    ↓
         │    [Backend: INSERT into terms_acceptance_audit]
         │    ↓
         │    [Backend: UPDATE usuario.accepted_terms_version = "1.0"]
         │    ↓
         │    [Frontend: redirect /dashboard]
         └─ User cierra modal sin aceptar
              ↓
              [redirect /login (logout)]
```

## Rate Limiting for Export + DPO

**Decision:**
- Export: 1 per user per 24 hours
- DPO Contact: 1 per IP per 30 seconds

**Implementation:**
```

Just decorate endpoints:
  @RateLimit(requests=1, windowSec=86400, identifier="user")  // export
  @RateLimit(requests=1, windowSec=30, identifier="ip")       // dpo
```

## Descartadas (Why NOT)

### ❌ Dynamic Terms update via admin UI
- Legal documents must be reviewed + signed-off
- Code review + merge = audit trail
- Admin UI = risky, no version control

### ❌ Anonimización de datos en export
- GDPR Art. 15 doesn't require anonymization
- Just return user's own data
- Privacy concern solved by rate limiting

### ❌ Reject Terms option
- Electoral system: mandatory participation
- If user rejects, logout (no "both options" UI)

### ❌ Cookies banner (separate task)
- T-COMPLIANCE-07 handles this
- This SDD focuses on legal docs + acceptance
